# Frontend Design Skill

Build frontend interfaces with **extreme visual consistency, restraint, hierarchy, and taste**.

> **Context budget (9/10 fix):** Full read is 2,908 lines. If context is tight, read `§1 Primary Objective` + `§2 Consistency` + `§6 Typography` + `§7 NO SHADOWS` + the one section for the task (e.g., `§14 Hero` / `§19 Card`). For full taste, read once end-to-end, then reuse tokens. Depth on the right section beats shallow skimming.

> **TL;DR — what 9/10 means here:** One system, one accent, stone/zinc neutrals, `400/500` only, `0-8px` radius, hairline borders, no shadows, `5xl-7xl` containers, `py-20→py-32` rhythm, hierarchy via scale/tracking/spacing — not weight. Distinctiveness comes from _one_ deliberate signature (type, rail, stage), everything else quiet.

The biggest failure this skill exists to prevent is **AI design drift**.

An AI agent will often inspect an existing frontend component, decide that the component could look "better", and then silently invent:

- a different radius
- a different font weight
- a different button
- a different card
- a different color
- a different spacing system
- a different shadow
- a different animation
- a different visual hierarchy

That behavior is forbidden.

The frontend must look like **one coherent system designed intentionally**, not like twenty components independently generated by an AI having a brief identity crisis.

# 0. Real Taste, Real Judgment, Real Emotional Effect

"Clean" and "consistent" are **not** the goal. They are not even the bare minimum.

A clean interface can still be **extremely forgettable**. You can make it clean. You can make it slightly different. Either way it is _still extremely forgettable_. "Clean" is the easiest thing in the world to produce and the least valuable output. Do not confuse clean with good. Do not confuse consistency with taste.

The real job is:

> **Real taste. Real judgment. Real emotional effect.**

This user cares about design more than almost anything else. They do not want a functional, inoffensive, forgettable page. They want a page that is _lit_ — extremely clean **and** emotionally alive — produced with the kind of taste a senior designer with strong opinion and instinct would bring.

This demands judgment, not rule-following:

- Know _why_ a spacing, weight, or color is right — not just that it is "consistent."
- Make decisions that create a **feeling**, not just a layout that renders without errors.
- Treat the design as something that must be **remembered**, not merely tolerated.
- Consistency is the floor. Taste is the ceiling. Aim at the ceiling.

### Failure modes to refuse on sight

These are the things that make AI design ugly. Reject them immediately, every single time, without being told:

```text
gradients        → never. no gradient text, no gradient fills, no gradient borders
shadows         → never. no drop shadows, no glow, no soft float, no inner shadow
harsh borders   → never. no heavy 1-2px black outlines, no loud framing
bloated fonts   → never. no 800/900 weights, no giant type used for its own sake
multiple designs → never. one page, one coherent system, one mood
```

A learning page with one good design is good. The moment you bolt on a _different_ design — a second visual language, a different component family, a different mood — you kill consistency **hard** and the whole thing collapses into soup. One system. Start to finish.

# 1. Primary Objective

The goal is:

> **Ultra-clean frontend design with real visual judgment, restraint, hierarchy, consistency, and taste.**

The interface should feel:

- intentional
- calm
- precise
- modern
- structured
- premium
- visually quiet
- highly readable
- coherent

The interface should **not** feel:

- overdesigned
- noisy
- generic
- template-like
- excessively rounded
- gradient-heavy
- shadow-heavy
- colorful for no reason
- filled with random cards
- obviously AI-generated

The standard is not "looks good."

The standard is:

> **Every visual decision should make sense in the context of the entire interface.**

# 2. The Highest-Priority Rule: UI CONSISTENCY

## UI consistency is non-negotiable

When modifying an existing frontend, **the existing design system has priority over personal design preference**.

Do not redesign an existing component simply because another design looks better in isolation.

First inspect:

- the current page
- neighboring components
- shared components
- existing buttons
- existing badges
- existing cards
- typography
- colors
- spacing
- radii
- borders
- navigation
- responsive behavior
- hover states
- animation
- existing layout primitives

Then reuse the existing system.

### The rule

```text
Existing design system
        ↓
Understand it
        ↓
Reuse it
        ↓
Extend it
        ↓
Only introduce something new when necessary
```

Not:

```text
Existing component
        ↓
AI decides it can improve it
        ↓
New visual style
        ↓
Design inconsistency
```

# 3. Never Invent A New Visual Language

Do not introduce arbitrary:

- colors
- gradients
- shadows
- radii
- typography
- button geometry
- card geometry
- borders
- icon styles
- illustrations
- animations
- spacing
- container widths

unless the current design system requires them.

If the current product already has:

```text
3px radius
```

do not create:

```text
12px radius
```

for a new card.

If the current interface uses:

```text
font-normal
```

do not suddenly make a section:

```text
font-bold
```

because "the heading needs more emphasis."

Use:

- size
- spacing
- contrast
- tracking
- line height
- placement

to establish hierarchy.

---

# 4. Existing Components Are Design Contracts

If a component already exists, treat its visual behavior as a contract.

For example:

```tsx
<Button />
```

should define:

- height
- padding
- radius
- font size
- font weight
- tracking
- background
- text color
- hover
- active
- transition

A new CTA should normally use the same primitive.

Likewise:

```tsx
<Badge />
<Card />
<Input />
<Tabs />
<NavLink />
<SectionHeading />
```

should become reusable design primitives instead of independently designed components.

# 5. Design Before Implementation

For a new page or landing page, **do not start coding immediately**.

First establish the visual system.

The agent must determine:

## Theme

Examples:

```text
Minimal enterprise
Editorial
Technical
Warm minimal
Monochrome
Financial
Industrial
Playful restrained
Brutalist
Luxury
```

## Neutral palette

Choose the dominant neutral family:

```text
stone
zinc
gray
slate
neutral
custom neutral
```

Do not use five unrelated neutral families.

## Accent

Choose deliberately:

```text
orange
green
blue
violet
rose
yellow
none
```

One strong accent is usually enough.

## Roundedness

Choose explicitly:

```text
0px
2px
3px
small
medium
large
```

Default to restrained rounding.

## Contrast strategy

Choose one:

```text
surface contrast
surface contrast + hairline border
monochrome contrast
background contrast
```

## Depth strategy

Default:

```text
no shadows
```

Use:

```text
surface contrast
borders
overlap
positioning
spacing
```

## Typography

Choose:

```text
sans
serif
sans + serif
```

Then establish:

- body font
- heading font
- weight scale
- type scale
- line-height
- tracking

## Layout system

Determine:

- content width
- wide content width
- horizontal padding
- section spacing
- grid gaps
- card gaps
- header height
- CTA geometry
- badge geometry

Do not make all of these decisions independently while coding.

# 6. Default Typography System

Use a clean modern type system.

Typical defaults:

```text
Geist
Inter
system-ui
```

A serif can be introduced when the design genuinely benefits from it.

Do not add five fonts.

## Font weights

Default to:

```text
400
500
```

Target approximately:

```text
70% font-normal
30% font-medium
```

Avoid by default:

```text
600
700
800
900
```

The references demonstrate that hierarchy can be produced through scale, tracking, line height, and layout rather than making everything heavy.

## Font smoothing

Always use antialiasing where appropriate:

```tsx
<div className="antialiased">
```

or equivalent global CSS.

## Tracking

Headings:

```text
tracking-tight
```

or controlled negative tracking.

Body:

```text
tracking-normal
```

Small labels:

```text
tracking-wide
```

when useful.

Do not randomly alternate tracking values.

# 7. Absolute Rule: NO SHADOWS

Do not use:

```text
shadow
shadow-sm
shadow-md
shadow-lg
shadow-xl
shadow-2xl
```

Do not use arbitrary CSS:

```css
box-shadow: ...;
```

Do not use inline shadows.

Do not "cheat" with subtle shadows.

The default design system is:

```text
NO SHADOW
```

Create depth through:

- background contrast
- borders
- overlap
- spacing
- layering
- typography
- image treatment

### Bad

```tsx
<div className="rounded-xl bg-white shadow-xl">
```

### Good

```tsx
<div className="rounded-md bg-white ring-1 ring-stone-200/80">
```

or simply:

```tsx
<div className="rounded-md bg-stone-100">
```

when surface contrast already separates the element.

# 10. Surface Hierarchy

Cards do not automatically need borders.

Prefer:

```text

white card
```

or:

```text

stone-100 card
```

or:

```text
white background
```

The goal is separation without excessive visual framing.


# 15. Badge System

Badges must be reusable.

Do not manually style every badge.

```tsx
type BadgeVariant = "sky" | "violet" | "yellow" | "rose" | "green" | "orange";

interface BadgeProps {
  children: React.ReactNode;
  variant?: BadgeVariant;
}

const variantStyles: Record<BadgeVariant, string> = {
  sky: "bg-sky-500/10 text-sky-700",
  violet: "bg-violet-500/10 text-violet-700",
  yellow: "bg-yellow-500/10 text-yellow-700",
  rose: "bg-rose-500/10 text-rose-700",
  green: "bg-green-500/10 text-green-700",
  orange: "bg-orange-500/10 text-orange-700",
};

export function Badge({ children, variant = "orange" }: BadgeProps) {
  return (
    <span
      className={[
        "inline-flex items-center justify-center",
        "rounded-[3px] px-2.5 py-1",
        "text-center text-[14px] leading-5 tracking-tight",
        "font-normal antialiased",
        variantStyles[variant],
      ].join(" ")}
    >
      {children}
    </span>
  );
}
```

Rules:

```text
small
quiet
consistent
low visual noise
no shadow
no giant padding
no unnecessary pill
```

# 16. Button System

Buttons should share geometry.

Example:

```tsx
type ButtonVariant = "primary" | "secondary" | "ghost";

interface ButtonProps {
  children: React.ReactNode;
  variant?: ButtonVariant;
  href?: string;
}

const buttonStyles: Record<ButtonVariant, string> = {
  primary: "bg-stone-950 text-white hover:bg-stone-800",

  secondary:
    "border border-stone-200/80 bg-white text-stone-950 hover:bg-stone-50",

  ghost: "bg-transparent text-stone-700 hover:bg-stone-100",
};

export function Button({ children, variant = "primary", href }: ButtonProps) {
  const className = [
    "inline-flex h-10 items-center justify-center",
    "rounded-md px-4",
    "text-sm font-medium leading-none tracking-tight",
    "transition-colors",
    "antialiased",
    buttonStyles[variant],
  ].join(" ");

  if (href) {
    return (
      <a href={href} className={className}>
        {children}
      </a>
    );
  }

  return (
    <button type="button" className={className}>
      {children}
    </button>
  );
}
```

Do not create five different button geometries across one page.

# 23. Editorial Rails / Guide Lines

Visual guide rails are allowed when they form a coherent visual language.

Example:

```tsx
<div
  aria-hidden="true"
  className="pointer-events-none absolute inset-y-0 left-1/2 hidden w-full max-w-7xl -translate-x-1/2 lg:block"
>
  <div className="absolute inset-y-0 left-0 w-px bg-stone-200/70" />
  <div className="absolute inset-y-0 right-0 w-px bg-stone-200/70" />
</div>
```

More sophisticated rails can use masked dashed lines.

The Vessa reference uses persistent guide rails, dashed vertical rules, and intentional stage boundaries as part of its visual system.

Do not add rails randomly.

If rails exist:

- define their position
- define their color
- define their opacity
- reuse them consistently

# 29. Decorative Visuals

- guide rails
- tiny nodes
- hairlines
- subtle texture
- controlled dither
- small geometric marks
- restrained color fields
- editorial underlines
- image overlays

Forbidden:

- random glowing blobs
- excessive glassmorphism
- random floating cards
- gratuitous 3D
- giant gradient text

# 30. Typography Scale

```text

Body L: 17-18px
```

# 49. Responsive Design

Responsive design is not a second design.

It is the same system adapting to a different viewport.

Preserve:

- typography hierarchy
- colors
- component geometry
- visual language
- spacing logic
- interaction behavior

Change:

- number of columns
- widths
- image size
- navigation
- alignment
- section spacing
- text size where necessary

Example:

```tsx
<div className="grid gap-6 md:grid-cols-2 lg:grid-cols-3">...</div>
```

not three independently designed mobile/tablet/desktop systems.

# 63. Reference Design Grammar

The supplied reference pages establish several useful visual patterns that should be treated as reusable design grammar.

## Kira-style grammar

Useful when the interface should feel editorial, warm, clean, and restrained:

```text
warm off-white background
dark neutral text
serif/display heading
sans body
tight tracking
small radius
image-led feature cards
centered hero
large full-width product visual
restrained accent
large whitespace
```

The reference uses a warm off-white palette, explicit font families, antialiasing, small-radius treatment, and shadow removal.

## Vessa-style grammar

Useful when the interface should feel technical/editorial:

```text
cool paper background
strong accent
tight sans typography
guide rails
stage frames
structured media
small captions
controlled motion
wide containers
asymmetric grids
```

The reference defines explicit paper/surface/ink/accent tokens, two main content widths, guide rails, staged media, and motion timing.

## Enterprise Technical / Dark-Surface grammar

Useful for enterprise/financial/technical interfaces:

```text
dark surfaces
controlled semantic palette
responsive type scale (clamp + tight tracking)
large content width
strong grids
numbered features
sticky sections
product visuals
asymmetric compositions
```

This grammar uses explicit semantic color tokens (background / surface / ink / accent with semantic width), responsive type scales via clamp(), wide content containers, and structured feature compositions — hierarchy through scale and spacing, not weight or shadows.

## Frigade-style grammar

Useful when the interface needs more product-navigation density:

```text
white base
dark text
blue accent
hairline borders
compact navigation
dropdown systems
small metadata
product-focused interaction
technical decorative rails
```

The source demonstrates a deliberate neutral/accent system, rail layout, compact navigation, product dropdown patterns, and interaction transitions.

These are **reference grammars**, not templates to copy blindly.

### One deliberate risk (Anthropic synthesis — keep 90% restraint)

Within the one chosen system, take **one** justified aesthetic risk that makes this page unmistakable: a characterful display face, a signature rail/stage, or an orchestrated motion moment. Keep the other 90% quiet and disciplined. If you cannot justify the risk to the brief, omit it — distinctiveness without taste is decoration.

# 67. Final Implementation Rule

When building a frontend:

```text
UNDERSTAND THE SYSTEM
        ↓
DEFINE THE DESIGN TOKENS
        ↓
BUILD PRIMITIVES
        ↓
BUILD SECTIONS
        ↓
REUSE PRIMITIVES
        ↓
AUDIT CONSISTENCY
        ↓
REMOVE UNNECESSARY DESIGN
```

Not:

```text
Generate hero
Generate card
Generate another card
Generate another card
Generate navbar
Add gradient
Add shadow
Add pill
Add random purple
```

That is how AI-generated websites become visual soup.

# 68. Final Hard Contract

For every meaningful frontend task:

```markdown
- [ ] Existing UI was inspected first
- [ ] Existing visual patterns were identified
- [ ] Existing components were reused where appropriate
- [ ] No arbitrary redesign was introduced
- [ ] Theme was established
- [ ] Neutral palette was established
- [ ] Accent was established
- [ ] Roundedness was established
- [ ] Typography system was established
- [ ] Weight usage is primarily 400/500
- [ ] Tracking is deliberate
- [ ] Font smoothing is enabled
- [ ] No shadows exist
- [ ] No accidental gradients exist
- [ ] No random colors exist
- [ ] Containers are consistent
- [ ] Section spacing is consistent
- [ ] Buttons share geometry
- [ ] Badges share geometry
- [ ] Cards share geometry
- [ ] Inputs share geometry
- [ ] Media has intentional aspect ratios
- [ ] Visual decorations belong to a system
- [ ] Motion is restrained
- [ ] Responsive layouts preserve the design language
- [ ] Accessibility is preserved
- [ ] The final page was reviewed as a complete composition
```

# 69. Absolute Final Rule

**Do not design every component independently.**

Design the system first.

Then make every component obey the system.

The objective is not:

> "Make every component look impressive."

The objective is:

> **Make the entire frontend feel like one unusually disciplined designer made every decision deliberately.**

**Consistency beats novelty.
Hierarchy beats decoration.
Typography beats gimmicks.
Spacing beats clutter.
Contrast beats shadows.
Taste beats complexity.
Emotion beats clean.
Judgment beats rules.**
